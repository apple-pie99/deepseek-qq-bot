# 真链路实测记录（模拟 NapCat → AstrBot → DeepSeek）

> 记录时间：2026-10-24 · 目的：在不装 NapCat 的情况下，验证"消息真的能走完整管道"，
> 并顺便把采样温度这件事量化。

测试方法：用 Python websocket 客户端扮演 NapCat，连 `ws://127.0.0.1:6199/ws`
（`Authorization: Bearer <token>`、`X-Client-Role: universal`），发 OneBot v11 群消息事件，
收 AstrBot 的 `send_group_msg` 动作。走的是完整管道，不是直连 API。

## 两个只有真链路才能发现的 bug

### 1. provider 模型条目必须单独写（严重）

`provider_sources` 只是「哪家 API + Key」，`provider` 才是「用哪个模型」。
`core/provider/manager.py:343` 启动时遍历的是 `self.providers_config`（即 config 的 `provider`）。
只写 `provider_sources` 时，日志会报「未找到任何可用的对话模型（提供商）」，所有消息都失败。

模型条目最小可用字段：

```json
{
  "id": "deepseek-chat",
  "type": "openai_chat_completion",
  "provider_type": "chat_completion",
  "provider_source_id": "deepseek",
  "model": "deepseek-chat",
  "enable": true
}
```

不要在这个条目里写 `key` 或 `api_base`——`get_merged_provider_config` 的合并规则是
`{**source, **provider}`，provider 优先，写空值会覆盖掉 source 里的真 Key。

### 2. 真链路与直连 API 的表现不同

`datetime_system_prompt` 默认开启，会注入当前时间。
直连 API 测试时它瞎猜「好像是四月」；真链路正确回答「10 月 24 号，星期六」。
`identifier` 开启后还会注入 `User ID / Nickname`。

## 温度实测（同一套 20 条探针，同一条链路）

| 温度 | 崩坏处数 | 具体表现 |
|---|---|---|
| 1.3 | 4 | 「写字的活，Turbo只会写训练笔记」（夹英文）；「让涡轮重跑给我看」（人称错）；「奶茶也得先赢了涡轮再说呢」（接不住）；「听不懂翻译中的意思，…蹄铁很起劲！买完之后全是气势！」（整段废句） |
| 1.0 | 0 | 20 条全部通顺、在角色内 |

结论：该人设在 1.3 下会稳定出现语义崩坏，1.0 干净。

> 注：模板 `preset/astrbot/provider_deepseek.json` 里仍写着 1.3（DeepSeek 官方对通用对话的推荐值）。
> 用人设时建议改成 1.0，或先用 `lib/persona_qa.py` 在 1.3 下跑一遍看你这套人设扛不扛得住。
> 复现方法：`DS_TEMP=1.3 python lib/persona_qa.py <人设文件>`。
